# RBPO-2026 — Система распределения мест в студенческом общежитии

**Вариант предметной области: 22**

## Описание проекта

RBPO-2026 — REST API для управления размещением студентов в общежитии. Приложение автоматизирует работу с пользователями, комнатами, заявлениями на проживание, договорами и запросами на перевод между комнатами.

Проект разработан на Java с использованием Spring Boot. В ходе выполнения заданий последовательно реализованы REST API, бизнес-логика предметной области, хранение данных в реляционной базе данных и механизмы аутентификации и авторизации.

## Используемые технологии

- Java 17
- Spring Boot 3.5.5
- Spring Web
- Spring Validation
- Spring Data JPA
- Spring Security
- PostgreSQL 16
- Maven
- HTTP Basic Authentication
- BCrypt
- REST API и JSON
- Postman

## Задание 1. Разработка REST API

На первом этапе разработан REST API для управления основными объектами предметной области — распределения мест в студенческом общежитии.

Реализована многослойная архитектура приложения, обеспечивающая разделение HTTP-обработчиков, бизнес-логики, моделей предметной области и доступа к данным.

Основные возможности:

- создание, просмотр, изменение и удаление пользователей;
- управление комнатами и их вместимостью;
- регистрация заявлений на проживание;
- управление договорами проживания;
- работа с запросами на перевод между комнатами;
- получение общей информации и статистики общежития;
- проверка входных данных и обработка ошибок REST API.

API принимает запросы в формате JSON и возвращает соответствующие HTTP-статусы.

## Задание 2. Бизнес-логика предметной области

На втором этапе реализованы правила работы общежития и операции, выходящие за рамки обычного CRUD.

Основные сущности предметной области:

- **User** — студент или сотрудник;
- **Room** — комната общежития с определённой вместимостью;
- **HousingApplication** — заявление на получение места;
- **ResidenceContract** — договор проживания;
- **RoomTransferRequest** — запрос на перевод в другую комнату.

В приложении предусмотрены состояния заявлений, договоров и запросов на перевод.

Основные правила предметной области:

- заявление должно быть связано с существующим пользователем;
- договор можно заключить только на основании одобренного заявления;
- при создании договора проверяется доступность комнаты;
- количество проживающих не должно превышать вместимость комнаты;
- завершение договора освобождает место;
- перевод возможен только при действующем договоре и наличии свободного места в целевой комнате;
- недопустимые изменения состояния объектов отклоняются.

Бизнес-логика сосредоточена в сервисном слое. Это позволяет проверять состояние связанных объектов и поддерживать согласованность данных при выполнении операций.

## Задание 3. Базы данных и отношения между таблицами

На третьем этапе приложение переведено на работу с реляционной базой данных PostgreSQL. Вместо хранения основных данных в структурах оперативной памяти используется постоянное хранение в таблицах базы данных.

Для взаимодействия с базой данных применяются Spring Data JPA и Hibernate.

### Структура базы данных

В базе данных представлены пять основных сущностей:

| Таблица | Назначение |
|---|---|
| `users` | Пользователи системы |
| `rooms` | Комнаты общежития |
| `housing_applications` | Заявления на проживание |
| `residence_contracts` | Договоры проживания |
| `room_transfer_requests` | Запросы на перевод между комнатами |

### Связи между сущностями

- Пользователь может иметь несколько заявлений на проживание.
- Заявление связано с пользователем, который его подал.
- Договор связан с заявлением и комнатой.
- Запрос на перевод связан с договором и целевой комнатой.
- Внешние ключи обеспечивают ссылочную целостность между связанными таблицами.

### Ограничения целостности

В модели данных предусмотрены следующие ограничения:

- уникальность адреса электронной почты пользователя;
- уникальность номера комнаты;
- положительная вместимость комнаты;
- обязательные связи между зависимыми сущностями;
- хранение значений перечислений в виде строк;
- проверка бизнес-условий перед изменением состояния объектов.

Для выполнения запросов приложение использует отдельную учётную запись PostgreSQL с ограниченными привилегиями. Параметры подключения задаются через переменные окружения, а не хранятся непосредственно в исходном коде.

В `src/main/resources/data.sql` подготовлены демонстрационные данные для проверки работы приложения.

### Бизнес-операции

В рамках третьего задания предусмотрены пять основных бизнес-операций:

1. **Подача заявления на проживание.** Создаётся заявление, связанное с пользователем. Повторная подача при наличии другого нерассмотренного заявления ограничивается.
2. **Заключение договора.** Проверяются одобрение заявления, существование комнаты, корректность периода проживания и наличие свободного места.
3. **Размещение студента в комнате.** Создание активного договора влияет на занятость комнаты; вместимость проверяется с учётом действующих договоров.
4. **Завершение договора.** Договор переводится в состояние `TERMINATED`, а место становится доступным для дальнейшего размещения.
5. **Одобрение перевода.** Проверяются активность договора и доступность целевой комнаты, после чего обновляются связанные данные.

Операции выполняются через сервисный слой с использованием транзакций там, где это необходимо для согласованного изменения данных.

## Задание 4. Аутентификация и авторизация в Spring Security

На четвёртом этапе в приложение интегрирован Spring Security. Реализованы аутентификация пользователей, проверка прав доступа, защита изменяющих запросов от CSRF и безопасное хранение паролей.

### Аутентификация

Для доступа к защищённым ресурсам используется HTTP Basic Authentication.

Учётные записи хранятся в PostgreSQL. Пароли не сохраняются в открытом виде: для их хеширования используется `BCryptPasswordEncoder` с настроенной стоимостью 12.

Реализована регистрация пользователей через `POST /api/auth/register`.

При регистрации:

- проверяется уникальность электронной почты;
- проверяется надёжность пароля;
- пароль хешируется перед сохранением;
- новой учётной записи назначается роль `STUDENT`;
- пользователь не может самостоятельно назначить себе роль `STAFF` или `ADMIN`.

Для проверки текущей учётной записи предусмотрен endpoint `GET /api/auth/me`.

### Защита CSRF

Для защиты запросов, изменяющих данные, используется механизм CSRF Spring Security с хранением токена в HTTP-сессии.

Получить токен можно через:

`GET /api/auth/csrf`

Для изменяющих запросов необходимо передавать полученный токен в заголовке `X-CSRF-TOKEN` и сохранять соответствующую cookie сессии.

CSRF-защита применяется совместно с HTTP Basic Authentication и существующими REST-контроллерами.

### Роли и разграничение доступа

В приложении предусмотрены три роли:

| Роль | Возможности |
|---|---|
| `STUDENT` | Регистрация, просмотр собственной учётной записи и доступ к открытой информации |
| `STAFF` | Управление основными объектами общежития и выполнение разрешённых бизнес-операций |
| `ADMIN` | Административный доступ к защищённым операциям |

Правила доступа задаются через `SecurityFilterChain` и аннотации `@PreAuthorize`.

Открытые endpoints предназначены для регистрации, получения CSRF-токена и чтения общедоступной информации. Операции управления данными требуют соответствующих полномочий.

Учётные записи сотрудников и администраторов могут создаваться при первоначальной настройке приложения через переменные окружения `APP_STAFF_*` и `APP_ADMIN_*`. Существующая учётная запись не должна автоматически получать повышенную роль только из-за повторного запуска приложения.

### Обработка ошибок безопасности

Приложение различает основные категории ошибок:

- **401 Unauthorized** — отсутствуют или неверны данные аутентификации;
- **403 Forbidden** — недостаточно полномочий либо отсутствует или неверен CSRF-токен;
- **409 Conflict** — операция нарушает бизнес-ограничения или конфликтует с текущим состоянием данных;
- **400 Bad Request** — запрос не проходит проверку входных данных;
- **404 Not Found** — запрашиваемый объект не найден.

Сообщения об ошибках не должны раскрывать пароли, хеши паролей, секреты подключения или другие чувствительные сведения.

## Запуск приложения

### Требования

Перед запуском установите:

- JDK 17;
- Maven;
- Docker и Docker Compose.

### Настройка окружения

1. Скопируйте файл `.env.example` в `.env`.
2. Укажите параметры подключения к PostgreSQL и задайте надёжные уникальные пароли для пользователей приложения, сотрудника и администратора.
3. Не добавляйте `.env` в систему контроля версий.

### Запуск базы данных

В корневой директории проекта выполните:

```bash
docker compose up -d db
```

### Запуск REST API

Экспортируйте переменные окружения и запустите приложение:

```bash
set -a && source .env && set +a
mvn spring-boot:run
```

После запуска API доступен по адресу:

`http://localhost:8080`

## Основные endpoints

| Endpoint | Назначение |
|---|---|
| `/api/auth/register` | Регистрация пользователя |
| `/api/auth/csrf` | Получение CSRF-токена |
| `/api/auth/me` | Информация о текущем пользователе |
| `/api/users` | Управление пользователями |
| `/api/rooms` | Управление комнатами |
| `/api/housing-applications` | Управление заявлениями |
| `/api/residence-contracts` | Управление договорами |
| `/api/room-transfer-requests` | Управление запросами на перевод |
| `/api/info` | Информация и статистика |

Для защищённых endpoints действуют правила авторизации, определённые в конфигурации Spring Security и сервисах приложения.
